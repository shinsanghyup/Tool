## 1. 개발 배경 및 의도

### 1-1. 시작 계기
- 팀 내부에서 "GPT-6 Astra(OpenAI 최신 멀티모달 모델)로 BIM 툴을 만들 수 있을까"라는 아이디어에서 출발.
- 다만 검토 결과, 풀 BIM 워크플로우(부재 속성체계, WBS 매칭, 협업 툴체인)는 조직 차원 도입이 필요한 무거운 작업이라 판단.
- **BIM은 완전히 배제**하고, 훨씬 현실적인 접근인 **"2D CAD 단면도 → 3D 시각화"** 방향으로 전환.
- AI 모델도 GPT 계열이 아닌 **Claude(Opus/Sonnet/Haiku)** 로 변경.

### 1-2. 최종 목적 (반드시 지켜야 할 원칙)
> **이 도구는 "이해를 돕는 시각화 보조 도구"이다. 구조계산·안정성 판단·설계 검토를 대체하지 않는다.**

- 사면·옹벽·흙막이 등 2D 단면 도면을 검토의견서에 첨부할 3D 투시도로 변환
- 발주처 설명, 팀 내부 회의에서 "이 단면이 입체로 어떻게 생겼는지" 직관적으로 보여주는 용도
- 최종 OK/NG 판단, 안정성 계산은 **항상 사람(엔지니어)이 별도로 수행** — 팀의 검토의견서 원칙(OK/NG는 명확히 사람이 판단)과 동일한 선상

### 1-3. 왜 이 방식인가 (사전 조사 결과 요약)
- 상용 솔루션(Buildots, OpenSpace 등)은 360도 카메라로 현장을 촬영해 AI가 BIM/공정표와 자동 대조하는 방식 → 하드웨어 투자와 조직 도입 부담이 큼
- 반면 "이미 갖고 있는 2D DXF 도면을 3D로 세워 보여주는" 접근은 입력이 이미 손에 있고, 결과물도 검토용으로 바로 쓸 수 있어 훨씬 가벼움
- CAD 파일(DXF)은 공개(open) 텍스트 포맷이라 좌표를 코드로 직접 파싱/생성 가능. 반면 DWG는 Autodesk 비공개 바이너리 포맷이라 직접 생성 불가 (아래 4-3 참조)

## 2. 현재까지 진행 상황 (필수 인수인계 내용)

### 2-1. 모델(AI) 오케스트레이션 원칙
작업 성격에 따라 아래 기준으로 모델을 자동 배분하기로 합의함 (매 작업마다 사람에게 확인하지 않고 자동 적용):

| 작업 | 모델 | 비고 |
|---|---|---|
| DXF 파싱, 좌표추출, 압출 로직, HTML 코드 생성 | **코드 (AI 호출 없음)** | 대부분의 실제 작업. 결정론적 처리라 AI 불필요 |
| 레이어명 자동분류 ("이 레이어가 옹벽 외곽선인가?") | **Haiku** | 단순 텍스트 분류, 반복 호출 시 저비용 (현재 미구현, 향후 확장 항목) |
| DXF 파싱 중 애매한 예외판단 | **Sonnet** | 필요시에만 호출 (현재 미구현) |
| 검토의견서용 최종 설명 문구 생성 | **Opus** | 문체 품질이 중요한 구간 (현재 미구현) |

- **토큰량 보고/모니터링 기능은 불필요** — 사용자 요청으로 제외 확정
- **작업마다 모델 확인받는 절차도 불필요** — 설계 단계에서만 상의하고, 실행 단계는 자동 진행하기로 확정
- 현재 프로토타입 단계에서는 실질적으로 **AI API 호출이 전혀 없음** — 전부 코드(파이썬/JS)로 처리됨. 향후 여러 도면을 배치 처리하게 되면 Haiku 자동분류부터 단계적으로 도입 예정

### 2-2. 입력 파일 관련 확인 사항
- **DWG가 아닌 DXF로 받는 이유**: DXF는 벡터 좌표가 텍스트로 그대로 들어있어 정확한 파싱 가능. PDF/이미지 스캔본은 AI가 도면을 "보고 추정"해야 해서 오차 위험 있음 → 원본 CAD(DXF) 파일을 우선 사용하는 것이 원칙
- 도면 안에 여러 도곽/단면이 섞여 있을 수 있으므로, 특정 단면만 지정할 때는 **① 텍스트 표기(제목/기울기 등) ② 레이어명 ③ 도곽 위치** 중 하나로 특정 가능

### 2-3. 실제 처리한 대상 도면 이력
1. **`20260909_옹벽단면.dxf`**: 도곽 4개(기울기 1:0 / 1:0.2 / 1:0.3 / 1:0.5)가 나란히 배치된 도면. 텍스트 엔티티 추출로 각 도곽의 기울기 표기를 확인함. (이 도면은 최종 3D화 대상으로 선택되지 않음)
2. **`지구_외_도로구간_축조식옹벽_단면도_현장.dxf`**: 사용자가 최종 선택한 도면. 안에 두 가지 요소가 혼재되어 있음을 확인:
   - "설치단면도"라는 제목의 콘크리트 옹벽 치수 표기(옹벽높이 2500mm 등) — **좌표(형상선)는 없음, 텍스트/치수선만 존재**
   - **"블록쌓기옹벽" 레이어** — 실제 좌표가 있는 형상 데이터 (기초 1단 + 블록 6단, 계단식 배면 구조)
   - 사용자가 "②번(블록쌓기옹벽)으로 진행"을 선택함

### 2-4. 추출한 최종 단면 좌표 (원본 DXF 좌표계 기준)
원본 DXF 좌표(x: 174212~174322, y: 281393~281590)를 원점(0,0) 기준으로 정규화한 값:

```
기초:      (0, 0) - (65.56, 0) - (65.56, 19.66) - (0, 19.66)
1단~5단:   폭 45.89, 각 단 높이 약 32.78 (19.66 → 183.57까지 5단)
6단(정상): 폭 20.49, 높이 183.57 → 196.68
배면:      계단식 후퇴 구조 (전면은 x=0 수직 유지)
```

최종 폐합 외곽선 (전면 수직, 배면 계단식):
```
(0.0, 0.0) → (65.56, 0.0) → (65.56, 19.66) → (45.89, 19.66)
→ (45.89, 183.57) → (20.49, 183.57) → (20.49, 196.68) → (0.0, 196.68) → 폐합
```

> 참고: 원본 도면에는 배면 성토 사면선(경사선, 좌표 (109.82,167.18)-(65.56,19.66))도 존재하지만, 이는 옹벽 몸체 자체가 아니라 배면 성토사면 표시이므로 **3D 압출 대상에서 제외**함. 필요시 향후 별도 참고선으로 추가 가능.

### 2-5. 좌표축 관례 (매우 중요 — 여러 차례 시행착오 발생한 부분)

**문제 발단**: 처음에는 "높이=Y, 압출(연장)방향=Z"로 3D화했더니, CAD(ZWCAD)에서 열었을 때 옹벽이 옆으로 누운 것처럼 보이는 문제 발생. 원인은 CAD 프로그램이 기본적으로 "Z=높이(하늘 방향)"로 인식하기 때문.

**확정된 최종 축 관례**:
| 축 | 의미 | 비고 |
|---|---|---|
| X | 옹벽 폭 (전면~배면) | 원본 DXF의 X와 동일 |
| Y | 압출(연장)방향 | 원본 DXF에는 없던 개념, 새로 부여 |
| Z | 높이 | 원본 DXF의 Y값을 Z로 옮김 (CAD 일반관례를 따름) |

**구현 방법**: Three.js의 `ExtrudeGeometry`는 기본적으로 XY평면 shape을 Z방향으로 압출하므로, 압출 후 `geometry.rotateX(Math.PI/2)`로 축을 재배치함 (`-PI/2`가 아니라 `+PI/2`인 이유: 처음에 `-PI/2`로 시도했더니 Z(높이)가 음수 범위로 나와 옹벽이 지면 아래로 파묻히는 문제가 발생했었음. 회전 방향을 반대로 하여 해결).

⚠️ **향후 다른 단면(사면, 흙막이 등)에 이 코드를 재사용할 때 반드시 이 축 변환 로직과 원본 도면의 X/Y 의미를 먼저 재확인할 것.**

### 2-6. 3D DXF Export 기능
- "3D DXF로 저장" 버튼 클릭 시 압출된 3D 메쉬의 모든 삼각형 면을 `3DFACE` 엔티티로 기록한 `.dxf` 파일을 브라우저에서 직접 생성·다운로드
- 삼각형은 3DFACE가 요구하는 4개 꼭짓점 중 4번째를 3번째와 동일하게 반복 입력하는 방식으로 처리
- 단(段) 구분선도 `LINE` 엔티티로 함께 기록됨 (레이어명: `COURSE_LINES`)
- **DWG는 직접 생성 불가** — DWG는 Autodesk의 비공개 바이너리 포맷이라 사양이 공개되어 있지 않음. 실무적으로는 DXF로 export한 뒤 AutoCAD 등에서 "다른 이름으로 저장 → DWG"로 변환하는 것이 유일한 방법 (1회 클릭으로 해결 가능한 수준이라 문제 되지 않는다고 판단)
- CAD(ZWCAD 등)에서 DXF를 열면 기본적으로 "평면도 + 2D 와이어프레임" 뷰로 보여서 입체로 안 보이는 이슈 발생 → 이는 파일 문제가 아니라 CAD의 표시 설정 문제. 사용자가 직접 뷰를 등각투영(Isometric)으로, 비주얼스타일을 음영처리(Shaded/Realistic)로 변경해야 함 (AutoCAD 계열 명령: `VSCURRENT`)
- DXF 저장 시 참고용으로 현재 화면의 PNG 스냅샷도 함께 자동 다운로드되도록 구현됨

### 2-7. 마우스 조작 관련 이슈 및 해결

**이슈 1 - 화면 전환이 너무 빠름**:
- 최초 감도(회전 0.006, 이동 0.0015, 관성감쇠 0.9)가 과도하게 민감했음
- 회전 감도 0.0018, 이동 감도 0.0006, 관성감쇠 0.75로 하향 조정하여 해결

**이슈 2 - 좌우회전이 잘 안 됨 (핵심 버그, 근본 원인 규명함)**:
- 원인: `THREE.Spherical` 객체는 **Y축을 극축(위쪽)으로 가정**하고 좌우회전(theta)을 계산하는데, 이 씬은 Z축이 높이(위쪽)인 좌표계를 쓰고 있어서 좌우회전이 의도한 축을 돌지 못하고 있었음
- 해결: 회전 계산 시에만 Y와 Z를 서로 바꿔치기(`toYUp`/`toZUp` 헬퍼 함수)해서 "가상으로 Y가 위쪽인 척" 계산한 뒤, 최종 카메라 위치를 실제 좌표계(Z가 위쪽)로 되돌려 적용하는 방식으로 수정
- 파이썬으로 회전 시뮬레이션 검증 완료: theta를 0~180도 돌려도 Z(높이)값이 고정된 채 카메라가 옹벽 주위를 수평으로만 도는 것을 확인함
- **리셋 버튼(`btnReset`)도 동일한 변환을 거치도록 함께 수정했음** — 초기에 이 부분을 놓쳐서 리셋 시에만 다시 버그가 재현되는 문제가 있었음. 향후 유사 컨트롤 코드 수정 시 리셋/초기화 버튼도 같이 확인할 것

## 6. 재개발 시 빠르게 파악할 핵심 3가지

다음에 이 프로젝트를 이어받는 사람(또는 미래의 자신)이 가장 먼저 알아야 할 것:

1. **이 도구는 계산기가 아니라 그림 도구다.** 안정성 판단, 구조계산은 절대 여기서 하지 않는다.
2. **축관례를 반드시 확인하라.** X=폭, Y=연장방향, Z=높이. 이걸 안 지키면 CAD에서 열었을 때 형상이 눕거나 파묻힌다 (2-5 항목 참조).
3. **Three.js에서 Z-up 좌표계를 쓸 때는 회전 컨트롤 코드에 특히 주의하라.** `THREE.Spherical`은 기본이 Y-up이라 별도 변환(`toYUp`/`toZUp`) 없이는 좌우회전이 정상 동작하지 않는다 (2-7 항목 참조).
